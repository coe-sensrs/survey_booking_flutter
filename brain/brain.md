  - **Phase 2 Auth & Security Complete & Verified**:
    - **Server-Mediated Auth Rate Limiting Gateway (Option A)**: Completely eliminated client-side bypass of rate limits. All three sensitive auth vectors (Login, Signup, Password Reset) are mediated through 2nd Gen Firebase Cloud Functions (`authenticateUser`, `registerApplicant`, `requestPasswordReset`) backed by a dedicated server-side rate limiting module (`functions/src/lib/rate_limit.ts`).
      - **Login (`authenticateUser`)**: Verifies credentials server-side via Google Identity Toolkit REST API (`signInWithPassword`) using secret `AUTH_WEB_API_KEY`. Enforces failure-based rate limiting stored in `/auth_rate_limits/{action}_{sha256(email)}`: Applicants locked out for 15 minutes after 5 failures (30m on repeat); Admins locked out for 30 minutes after 3 failures (60m on repeat). On success, mints a Firebase Custom Token (`auth.createCustomToken(uid)`), resets failure counter, and Flutter signs in via `_firebaseAuth.signInWithCustomToken()`.
      - **Signup (`registerApplicant`)**: Creates Auth user via Admin SDK, provisions `/users/{uid}`, mints custom token, and enforces count-based limit (max 3 signups per email per hour).
      - **Password Reset (`requestPasswordReset`)**: Dispatches Firebase-branded password reset email via Identity Toolkit REST API (`sendOobCode`), enforcing max 3 reset requests per email per hour. Silently succeeds on missing accounts to prevent email enumeration.
      - **Client Integration (`AuthFunctionsService`)**: Flutter calls unauthenticated Cloud Functions via `AuthFunctionsService` (`lib/core/services/auth_functions_service.dart`), translating `resource-exhausted` into `AuthRateLimitFailure(message, secondsRemaining)`.

    - **Client-Side HttpsCallable Constraint**: In Flutter's `cloud_functions` plugin, `HttpsCallable.call()` asserts `_debugIsValidParameterType(parameters)`, which strictly allows only standard JSON primitives (`null`, `num`, `bool`, `String`, `Map`, `List`). Passing a `cloud_firestore` `Timestamp` object (often generated by standard model `.toMap()` methods) causes an immediate assertion crash before network dispatch: `Failed assertion: line 34 pos 12: '_debugIsValidParameterType(parameters)': is not true`.
    - **Dual Serialization Architectural Pattern (`toMap()` vs. `toJson()`)**: Domain models (`Appointment`, `KmlFile`, `PermissionDocument`, `Logistics`, `XenDetails`) must decouple Firestore SDK writes from Cloud Functions payloads:
      - `.toMap()`: Used strictly for direct Firestore writes; outputs Firestore `Timestamp` objects (`Timestamp.fromDate(...)`) for dates.
      - `.toJson()`: Used strictly for Cloud Functions / HTTP transport; outputs ISO-8601 strings (`.toIso8601String()`) and delegates `.toJson()` down the model hierarchy.
    - **Backend Re-Hydration Invariant (`submitAppointment.ts`)**: Any Cloud Function receiving ISO-8601 string dates from the client must explicitly convert them back into Firestore `Timestamp` objects (`Timestamp.fromDate(new Date(stringVal))`) before writing to Firestore collections. If stored as raw strings in Firestore, client stream queries using `fromMap` will crash with: `type 'String' is not a subtype of type 'Timestamp?' in type cast`.

      ```dart
      uploadedAt: map['uploadedAt'] is Timestamp
          ? (map['uploadedAt'] as Timestamp).toDate()
          : (map['uploadedAt'] is String
              ? DateTime.tryParse(map['uploadedAt'] as String) ?? DateTime.now()
              : DateTime.now())
      ```
  - **Firebase Storage Rules 2-Read Cap & Pre-Generated Appointment ID Synchronization (`StorageException -13021 / Permission Denied`)**:
    - **Dual Root Causes of KML/Doc Read 403s**:
      1. *Storage Rules 2-Firestore Read Quota Violation*: Firebase Storage rules strictly enforce a limit of **at most two Firestore document reads** (`firestore.get()` / `firestore.exists()`) per rules evaluation. In `storage.rules`, when an applicant attempted to read a file, `isAssignedCommittee(appointmentId)` unconditionally called `let appt = firestore.get(...)` (Read 1) before checking `isCommittee()`. Because the user was an applicant, `isCommittee()` evaluated to `false`, and evaluation proceeded to `isOwningApplicant(appointmentId)`, which invoked `firestore.exists(...)` (Read 2) and `firestore.get(...)` (Read 3). The 3rd read crashed the rules engine with a quota violation, returning an immediate `403 Permission denied.`
      2. *Storage Path vs Firestore Document ID Desynchronization*: In `BookingWizardViewModel.submitBooking()`, files were uploaded using `tempId = DateTime.now().millisecondsSinceEpoch.toString()`, storing objects at `appointments/<tempId>/kml/<file>`. The backend Cloud Function `submitAppointment` then generated a brand new auto-generated ID (`db.collection('appointments').doc()`, e.g. `xyz123`). As a result, document `/appointments/<tempId>` never existed in Firestore, causing `isOwningApplicant` to return `false` on all lookup attempts.
    - **Tri-Partite Resolution Architecture**:
      1. *Client ID Pre-Generation (`AppointmentWriter.newAppointmentId()`)*: In `BookingWizardViewModel`, the real Firestore appointment ID is generated *before* upload via `appointmentRepo.newAppointmentId()` (which delegates to `_firestore.collection('appointments').doc().id`). KML and permission files are uploaded to `appointments/<appointmentId>/...`, matching the Firestore document path.
      2. *Backend Function Adoption (`submit_appointment.ts`)*: `SubmitAppointmentData` accepts optional `appointmentId?: string`. When provided, the Cloud Function binds `appointmentRef = db.collection('appointments').doc(data.appointmentId.trim())`, ensuring Storage and Firestore paths are 100% synchronized.
      3. *Storage Rules Hardening & Optimization (`storage.rules`)*:
         - *Short-Circuit Committee Check*: `isAssignedCommittee(appointmentId)` evaluates `isCommittee() &&` first, allowing applicants to short-circuit with **0** Firestore reads.
         - *Direct Uploader Metadata*: Added `isUploader()` checking `resource.metadata.uploadedBy == request.auth.uid`. `StorageUploadService` attaches `uploadedBy: uid` during upload, providing instantaneous authorization with **0** Firestore reads.
         - *Orphan / Legacy Document Fallback*: Added `isUnlinkedAppointmentFile(appointmentId)` (`isAuthenticated() && isEmailVerified() && !firestore.exists(...)`), allowing verified applicants to open pre-creation or legacy submissions (created with `tempId`) without permission denial.
