# Technical Decisions

- Component metadata uses SemVer while the toolkit release keeps CalVer.
- `manifest.json` and `manifest.lock.json` must remain synchronized with component frontmatter.
- **Global UI Snackbars**: Use `AppSnackbar` (`lib/core/utils/app_snackbar.dart`) powered by `awesome_snackbar_content` for all UI notifications (success, error, warning, info) instead of raw `ScaffoldMessenger.of(context)`. `MaterialApp.router` uses `AppSnackbar.scaffoldMessengerKey` for global context-less display when needed. Named parameters (`title:`, `message:`) must be used for consistency.
- **Auth Flow Routing**: Uses Exception-Driven Routing (`EmailNotVerifiedException`) from `AuthViewModel` to the UI to handle unverified emails. The Firebase session is intentionally kept alive for unverified users to facilitate smooth `user.reload()` checks and 60-second cooldown resend mechanisms without prompting for credentials again.
- **Applicant Persistent Bottom Navigation**: Implemented via GoRouter `StatefulShellRoute.indexedStack` with `ApplicantShellScreen`, managing 4 core branches: Home (`/home`), My Bookings (`/my-bookings`), Details (`/appointment-detail`), and Profile (`/profile`). Tab state and scroll positions are retained across switches. Multi-step wizards (e.g., the 9-Step Booking Wizard) remain pushed as modal routes over the shell to prevent accidental abandonment.
- **Admin Persistent Bottom Navigation**: Implemented via GoRouter `StatefulShellRoute.indexedStack` with `AdminShellScreen`, managing 4 core branches: Dashboard (`/admin-dashboard`), Committees (`/admin-committees`), Add Member (`/admin-add-member`), and Settings (`/admin-settings`).
- **Cross-Tab Appointment Inspection**: Managed via `selectedAppointmentIdProvider` (`NotifierProvider<SelectedAppointmentNotifier, String?>`). Tapping an appointment in Home or My Bookings sets the active ID and opens the detail view; the Details tab falls back gracefully to the latest booking or an empty state CTA.
- **Applicant Profile & Photo Lifecycle**: `ProfileScreen` & `ProfileViewModel` manage applicant profile details, photo uploads, and photo removals with end-to-end optimizations:
  1. `FilePicker` selects JPG/JPEG/PNG/WEBP under 5MB.
  2. `ImageCropper` crops the selection to a 1:1 square ratio (`maxWidth: 512, maxHeight: 512`).
  3. `StorageUploadService._compressImage` resizes (max 1024px) and compresses (JPG 70% quality) prior to upload to `users/{uid}/profile/`.
  4. `ProfileViewModel.uploadProfilePhoto()` captures the prior `photoUrl`, saves the new download URL to `users/{uid}.photoUrl` in Firestore, and subsequently deletes the old storage asset via `storageUploadService.deleteFileByUrl()`.
  5. `ProfileViewModel.deleteProfilePhoto()` removes the storage file via `storageUploadService.deleteFileByUrl()`, calls `UserRepository.deleteProfilePhoto()` using Firestore `FieldValue.delete()`, and triggers `ref.invalidate(authViewModelProvider)`.
  6. `ProfileScreen` shows a `Material`-backed modal bottom sheet (`_showPhotoOptionsSheet`) offering "Upload New Photo" and "Remove Photo" (with confirmation dialog) if a photo exists, or triggers direct upload if none exists.
  7. Upload/deletion progress is observed globally via `ref.watch(profileViewModelProvider).isLoading` so loading spinners survive back navigation and widget disposal without state loss.
  8. Display uses `SafeProfileAvatar` (`lib/core/widgets/safe_profile_avatar.dart`) which passes `FirebaseAppCheckSetup.httpHeaders`, displays download progress, and gracefully renders fallback styling on error or malformed URL.
- **Firebase Security & Storage Rules**: `storage.rules` enforces path-based access control (`isOwner(uid)`), MIME verification (`image/(jpeg|png|webp|jpg)`), and strict size caps (5MB for images/docs, 15MB for KML/KMZ). `firestore.rules` enforces email verification for bookings, restricts self-signup roles, prevents user privilege escalation on `update`, validates `photoUrl` with regex `matches('^https://.*')` (1-1000 length), and enables collection group queries on `auditLog`.
- **Booking Wizard Hive Draft Persistence & Resume Flow**: `BookingWizardViewModel.build()` loads drafts synchronously from Hive (`wizard_draft_box`), ensuring that if the app is killed at any step (1–8), all entered values, file paths, and current step are preserved. `HomeScreen` checks `hasDraft` to display a "Resume (Step X)" CTA and a "New" survey option with a discard confirmation dialog. `submitBooking()` safely validates local file existence before upload.
- **FlexColorScheme Material 3 Theme Architecture**: Migrated theme engine to `flex_color_scheme: ^8.4.0` using `FlexScheme.greenM3`, `FlexSubThemesData` for declarative component theming (interaction effects, tinted disabled controls, M2-style divider in M3, filled input decorators with 10dp radius and 16x14 padding, 10dp button corner radii, 12dp card radius, and navigation bar label behavior), GoogleFonts Inter typography, and `ResponsiveTheme.fromTheme(...)` scaling. 50dp button minimum heights are enforced via `ThemeData.copyWith` overrides on `elevatedButtonTheme` and `outlinedButtonTheme`. Custom generated `lightColorScheme` and `darkColorScheme` are stored in `lib/core/theme/app_colors.dart`, and semantic status colors are isolated in `AppStatusColors`.
- **Password Reset Flow & Abuse Protection**: `ApplicantLoginScreen` validates email format via `Validators.validateEmail`, properly awaits `resetPassword()` inside a `try/catch` block, enforces a 60-second countdown cooldown timer to prevent `too-many-requests` rate-limiting and OOB action code invalidation collisions, and provides in-flight loading spinners with `AppSnackbar` notifications.
- **Proactive Session Lifecycle & Deactivated User Guard**: Auth stream uses `FirebaseAuth.instance.userChanges()` across `AuthViewModel` and `app_router.dart` (`AsyncAuthNotifier`) to react to token refreshes, profile updates, and revocations. On emission, `AuthViewModel` checks if `appUser.active == false` in Firestore, immediately triggering `_forceSignOut()` for deactivated accounts and binding `user_id` / `role` keys in `CrashReportingService` (resetting to `'none'` on logout). `SurveyDeskApp` (`main.dart`) employs an `AppLifecycleListener` on resume (`onResume`) to call `validateCurrentSession()`, executing `user.reload()` and validating the Firestore `active` status to catch external deactivations while the app was backgrounded.
- **Full Logout & Shared Device Isolation (Option 3)**: On explicit `logout()` or forced session revocation (`_forceSignOut`), `HiveStorageService.clearUserData()` completely wipes all local storage (`_cacheBox` and `_wizardDraftBox`). `BookingWizardViewModel` listens to `authViewModelProvider` to reset in-memory wizard state to `const WizardStateData()` when the user logs out, ensuring strict privacy isolation on shared hardware.
- **Riverpod Real-Time Stream & Mutation Controller Pattern**: For complex detail views that require live Firestore document streaming alongside multiple administrative write operations (e.g., `AdminAppointmentDetailScreen`), real-time read state is separated into a `StreamProvider.family` (`adminAppointmentDetailStreamProvider`) and mutation actions into an imperative `Controller` provider (`adminAppointmentDetailControllerProvider`). This decouples UI streaming from action execution and avoids Riverpod 2.x `FamilyNotifier` / `AsyncNotifier.family` type-matching errors.
- **Secure Committee Member Provisioning & Credentials Presentation**: Committee members cannot be created via public client-side signups. Creation is handled exclusively through `createCommitteeAccount` 2nd Gen callable Cloud Function (`functions/src/index.ts`) triggered from `AddCommitteeMemberScreen` / `CommitteeManagementViewModel` via `AdminFunctionsService`. The function enforces admin RBAC guards (JWT claim check with Firestore `/users/{uid}` fallback & backfill), validates input data (name, email, 10–15 digit phone, expertise tag), creates the user in Firebase Auth with `emailVerified: true`, mints `role: 'committee'` custom claims, writes the Firestore `/users/{uid}` document, generates temporary credentials (`tempPassword` and optional `resetLink`), and provides automatic orphaned Auth user rollback on Firestore write failure. The response is returned to `AddCommitteeMemberScreen` which presents a non-dismissible modal (`_showCredentialsDialog`, `barrierDismissible: false`) displaying Name, Email, and Temporary Password in `SelectableText` format, accompanied by a one-touch "Copy" button (`Clipboard.setData`). Form clearing and navigation back to `/admin-committees` occur strictly after the admin confirms via "Done", with explicit `if (!mounted) return;` guards preventing memory leaks and use-after-unmount errors across async gaps.
- **Admin Cloud Functions Service & Cloud Run 2nd Gen IAM Infrastructure Resolution**:
  1. **Client Gateway**: All admin-level Cloud Function invocations route through `AdminFunctionsService` (`lib/core/services/admin_functions_service.dart`). It verifies local `authState.value?.isAdmin == true` before network dispatch, confirms `FirebaseAuth.instance.currentUser != null`, and forces a token refresh via `user.getIdToken(true)` to prevent expired or stale claims from triggering `unauthenticated` exceptions.
  2. **Error Translation**: Raw `FirebaseFunctionsException` codes are translated into domain `Failure` types (`already-exists` / `invalid-argument` -> `ValidationFailure`, `permission-denied` / `unauthenticated` -> `AuthFailure`, `not-found` -> `ServerFailure`, `unavailable` / `deadline-exceeded` / `internal` -> `NetworkFailure`).
  3. **Cloud Run 2nd Gen IAM Configuration**: 2nd Gen Cloud Functions run on Google Cloud Run, which defaults to rejecting non-GCP IAM tokens. Callable functions must declare `invoker: "public"`, `cors: true`, and `enforceAppCheck: false` in `onCall` options. If GCP organization policies (`constraints/iam.allowedPolicyMemberDomains`) block public invocations, unauthenticated invocations must be manually allowed in the Cloud Run service security settings.
  4. **Compute Engine Service Account Roles**: Cloud Functions 2nd Gen execute under `<project-number>-compute@developer.gserviceaccount.com`. The service account must be granted the `Firebase Admin` (or `Cloud Datastore User`) IAM role to prevent `7 PERMISSION_DENIED` errors when accessing Firestore and Auth via `firebase-admin`.
- **File Picker v12 Migration & Optional Multi-Document Upload**: Updated to `file_picker: ^12.0.0` federated architecture using `FilePicker.pickFile()` for single files and `FilePicker.pickFiles()` for batch picking. Step 7 permission documents are fully optional (`ValidationConstants.minPermissionDocsCount = 0`), with client-side individual file size validation (`<= 5MB`), allowed extension verification (`pdf`, `jpg`, `jpeg`, `png`), deduplication, and slot overflow clamping (`max 5`).
- **Transparent Upload Progress & Firebase Storage MIME Metadata**: `StorageUploadService` and `BookingWizardViewModel.submitBooking` track upload bytes via `onProgress` callbacks. `Step8Review` renders a real-time progress card with an animated `LinearProgressIndicator` and step descriptions during slow network uploads. Explicit `SettableMetadata(contentType: ...)` is attached to all uploads to guarantee compliance with `storage.rules`.
- **StatefulShellRoute Branch Back Button Interception**: In GoRouter `StatefulShellRoute.indexedStack`, each branch operates in its own isolated `Navigator`. When at the root of a non-home branch (e.g. My Bookings, Details, Profile in Applicant; Committees, Add Member, Settings in Admin), pressing Android/system back triggers GoRouter to exit the app if outer shell `PopScope` is bypassed. To enforce standard tab navigation, all non-home branch routes in `app_router.dart` are wrapped in `PopScope(canPop: false, onPopInvokedWithResult: ...)` to switch to Home/Dashboard (`index: 0`), allowing a subsequent back press on Home to exit the app.
- **Two-Phase Role-Aware Routing & Zero-Flash Native Splash Lifecycle**: `AsyncAuthNotifier` blocks router redirects until both `userChanges()` emission and Firestore `/users/{uid}` role document lookup complete (`isLoading = false`), preventing race conditions on app startup. `initialLocation` in GoRouter is set to `AppRoutes.login` (`/login`), and while `isLoading = true`, redirect holds on `/login` rather than returning `null` (which would have exposed unauthorized shells). To eliminate any splash-before-redirect race condition, `AsyncAuthNotifier` calls `notifyListeners()` first to let GoRouter resolve the redirect to the role shell (`/home`, `/admin-dashboard`, `/committee-dashboard`), and removes the native splash inside `WidgetsBinding.instance.addPostFrameCallback((_) => FlutterNativeSplash.remove())` after the destination screen is painted. Unauthenticated users see only `/login` with 0ms visual jumping. `AdminLoginScreen` performs explicit `context.go(AppRoutes.adminDashboard)` (admin) or `context.go(AppRoutes.committeeDashboard)` (committee) on `AsyncData` for instant UI feedback. Unverified applicants are redirected to `/verify-email`.
- **Riverpod Stream Subscription in Notifier `build()`**: Never pass `fireImmediately: true` to `ref.listen` inside a Notifier's `build()` method if the callback references `state` (e.g. `state = state.copyWith(...)`), because the callback executes synchronously during `ref.listen` before `build()` has returned, throwing `StateError: Tried to read the state of an uninitialized provider`. Instead, initialize state with synchronous `ref.read(...)` in `build()` and allow `ref.listen` to handle subsequent updates.
- **Server-Mediated Auth Rate Limiting Gateway (Option A)**:
  1. **Threat Model & Motivation**: Direct client calls to Firebase Auth SDK (`signInWithEmailAndPassword`, `createUserWithEmailAndPassword`, `sendPasswordResetEmail`) communicate with Google's Identity Toolkit endpoints using the public web API key. Any client-side rate limit or pre-flight check can be bypassed by an attacker issuing direct HTTP requests.
  2. **Cloud Functions Gateway**: All sensitive auth operations are routed through 2nd Gen HTTPS Callable Cloud Functions (`authenticateUser`, `registerApplicant`, `requestPasswordReset`) backed by a dedicated server-side rate limiting module (`functions/src/rate_limit.ts`).
  3. **Credential Verification**: Because the Firebase Admin SDK does not provide a `verifyPassword()` method, `authenticateUser` calls Google's Identity Toolkit REST API (`/accounts:signInWithPassword`) server-side using the `AUTH_WEB_API_KEY` secret parameter. On success, it mints a Firebase Custom Token (`auth.createCustomToken(uid)`), and Flutter establishes the session via `_firebaseAuth.signInWithCustomToken()`.
  4. **Rate Limit Policies**:
     - *Applicant Login*: 5 failures -> 15-minute lockout (30-min on repeat).
     - *Admin Login*: 3 failures -> 30-minute lockout (60-min on repeat).
     - *Signup*: 3 accounts per email per hour.
     - *Password Reset*: 3 requests per email per hour (+ 60s client-side cooldown retained for UX).
  5. **Storage Schema & PII Protection**: Stored in `/auth_rate_limits/{action}_{sha256(email)}` in Firestore using SHA-256 hashed emails. Locked down via `firestore.rules`: `allow read, write: if false;` (accessible exclusively via Admin SDK).
  6. **Client Gateway (`AuthFunctionsService`)**: `lib/core/services/auth_functions_service.dart` handles unauthenticated function calls, translating `resource-exhausted` errors into `AuthRateLimitFailure(message, secondsRemaining)`. `ApplicantLoginScreen` and `AdminLoginScreen` display live lockout countdowns on the Login button (`Locked (Xs)`).
  7. **Secret Naming Convention (`AUTH_WEB_API_KEY`)**: The Firebase CLI rejects custom secret names starting with `FIREBASE_`, `X_GOOGLE_`, or `EXT_`. Use `AUTH_WEB_API_KEY` set via `firebase functions:secrets:set AUTH_WEB_API_KEY`.
  8. **Cloud Run 2nd Gen Public Invocations & Domain Restricted Sharing**: 2nd Gen Cloud Functions require `invoker: "public"` (`roles/run.invoker` for `allUsers`) because unauthenticated mobile users do not possess Google Cloud corporate IAM employee accounts (`@sensrs.com`). Network reachability grants access to the container; authorization is enforced inside function logic (password verification, atomic rate limiting, role checks) and App Check. When deploying under Google Workspace orgs, `constraints/iam.allowedPolicyMemberDomains` blocks automated CLI assignment of `allUsers`. To resolve, either enable "Allow unauthenticated invocations" on each service in the Cloud Run Console, or override the organization policy at the GCP project level.
  9. **ESLint Predeploy Standard (`functions/.eslintrc.js`)**: Configured with 4-space indentation (`"indent": ["error", 4]`), `max-len: 120`, and disabled deprecated JSDoc rules (`require-jsdoc: 0`, `valid-jsdoc: 0`) to prevent predeploy hook failures (`ENOENT` on Windows).

- **Server-Mediated Appointment Status Mutations & Zero-Layout-Shift Committee Review UX**:
  1. **Root Cause Analysis (Optimistic Revert Bug)**: When a committee member tapped "Approve" (or Reject / Clarify), the button disappeared and shortly after reappeared with status remaining `under_review`. This occurred because `firestore.rules` enforces `allow update: if false;` on `/appointments/{id}`. The client-side Flutter code was previously attempting direct Firestore updates via `_firestore.collection('appointments').doc(id).update(...)`. The local Firestore SDK optimistically applied the change, hiding the button, but the server rejected the write (`permission-denied`), rolling back the document and causing the button to reappear.
  2. **Server-Side Cloud Functions Gateway (`reviewAppointment`, `submitClarificationReply`, `admin_appointment_mutations.ts`)**:
     - `reviewAppointment` (2nd Gen Callable): Handles approve, reject, and request clarification actions. Verifies caller is assigned reviewer (`assignedReviewerId == uid` or admin). Verifies status is `under_review`. In an atomic transaction: transitions status, records reviewer action in `/appointments/{id}/auditLog`, and if approved or rejected, atomically decrements the applicant's booking quota in `rateLimits/{applicantId}.pendingCount`.
     - `submitClarificationReply` (2nd Gen Callable): Handles applicant responses, validates caller ownership (`applicantId == uid`), verifies status is `clarification_requested`, ensures single reply limit, updates status back to `under_review`, and logs to `auditLog`.
     - Admin mutations (`assignReviewer`, `setConfirmedDate`, `assignFieldworkTask`): Validates admin privileges and performs atomic updates with audit logs.
  3. **Client Repository Migration (`FirebaseAppointmentRepository`)**: Replaced all direct `_firestore.collection('appointments').doc(id).update(...)` calls with `_functions.httpsCallable(...)` calls.
  4. **Zero-Layout-Shift & Defensive UX in Committee Review**:
     - Inline loading spinners retain the exact button geometry (fixed height/width constraint) instead of replacing the entire button widget with an unconstrained `CircularProgressIndicator`, preventing layout shifts.
     - Added `_showApproveDialog` confirmation modal to prevent accidental approvals.
     - Integrated `AppSnackbar` for clear user feedback on success or failure.
     - Viewmodel triggers `ref.invalidate(committeeDashboardStreamProvider)` to keep the committee reviews queue synchronized.
  5. **ESLint Predeploy & Deployment Resolution**: Predeploy ESLint errors (`object-curly-spacing`, `block-spacing`, and multiline `max-len`) in `functions/src/` resolved via `npx eslint src --fix` and multi-line export formatting in `index.ts`. All 10 Cloud Functions deployed cleanly to Firebase project `surveybookingapp`.
- **Firestore Identity-Based Appointment Reads & Custom Token Claims Synchronization**:
  1. **Root Cause Analysis (Appointment Query PERMISSION_DENIED on Startup)**: When an applicant launched the app, `HomeViewModel.build()` called `getUpcomingSurveysForApplicant` and `getRecentRequestsForApplicant`. Both failed with `PERMISSION_DENIED`. The root cause was that `firestore.rules` required `isApplicant()` (`request.auth.token.role == 'applicant'`) to read `/appointments/{id}`. For existing/cached sessions, users created via Console, or custom tokens minted without developer claims, `request.auth.token.role` is absent. In Firestore query analysis, rules act as queries filters: if `isApplicant()` evaluates to `false`, Firestore cannot prove that all documents matching `.where('applicantId', isEqualTo: auth.uid)` are allowed, immediately rejecting the query.
  2. **Security Rules Decoupling**: Updated `firestore.rules` appointment read rule to use direct cryptographic identity ownership: `allow read: if isAdmin() || (isAuthenticated() && resource.data.applicantId == request.auth.uid) || (isCommittee() && ...)`. This matches the established patterns in `auditLog` and `storage.rules`, eliminating token-claim fragility on self-owned data reads.
  3. **Token Key Presence Defense**: Hardened `isAdmin()`, `isCommittee()`, and `isApplicant()` to check `'role' in request.auth.token` before indexing into `role`, avoiding rule evaluation errors. Added `exists(...)` guard in `auditLog` subcollection rule prior to `get(...)`.
  4. **Backend Token Minting & Self-Healing Sync**: Updated `authenticateUser` Cloud Function to sync custom claims (`await auth.setCustomUserClaims(uid, {role: userRole})`) and pass developer claims to `createCustomToken(uid, {role: userRole})`. In `submitAppointment` and `submitClarificationReply`, added self-healing Firestore profile lookups to resolve and set missing custom claims automatically.
  5. **Automated Unit Tests**: Expanded `firebase/tests/firestore/appointments.rules.test.js` with 4 new test assertions (`APPLICANT_NO_CLAIMS`) verifying that claim-less tokens can read their own appointments and query by `applicantId`, but cannot read others' data or query unfiltered (total test suite expanded to 112 assertions across 8 suites).
- **Committee Review Execution, Firestore Read-Before-Write Transaction Order & ID Token Refresh**:
  1. **Root Cause Analysis (Approve Failed: Internal Error & Session Expired)**: Tapping "Approve" in `CommitteeReviewDetailScreen` experienced a layered progression of blockers:
     - *Layer 1 (Session Expired / Unauthenticated)*: Mobile client called `reviewAppointment` with cached or stale ID tokens, combined with Cloud Run 2nd Gen requiring corporate IAM authentication because Google Workspace Domain Restricted Sharing blocked `allUsers` (`roles/run.invoker`), and an un-registered App Check debug token. Resolved by implementing `_refreshToken()` (`await user.getIdToken(true)`) wrapped in try-catch in `FirebaseAppointmentRepository`, registering the debug token in Firebase Console, and allowing public invocations on Cloud Run.
     - *Layer 2 (Internal Error)*: Once authentication passed and the Cloud Function was executed, the function threw an unhandled exception wrapped as `INTERNAL` (`Approve failed: Internal error`). Google Cloud Firestore strictly requires that **all transaction reads (`txn.get()`) must execute before any transaction writes (`txn.update()`, `txn.set()`, `txn.delete()`)**. In `review_appointment.ts`, line 151 executed `txn.update(appointmentRef, updates)`, and line 158 subsequently executed `await txn.get(rateLimitRef)` to restore the applicant's booking quota (`rateLimits/{applicantId}.pendingCount`). Firestore threw an uncaught `Error: Firestore transactions require all reads to be executed before all writes`.
  2. **Strict Two-Phase Transaction Architecture**: Re-architected `functions/src/functions/appointments/review_appointment.ts` into two separate phases inside `db.runTransaction`:
     - *Phase 1 (All Reads)*: Reads `appointmentSnap = await txn.get(appointmentRef)`, validates preconditions, and reads `rateLimitSnap = await txn.get(rateLimitRef)` for quota restoration before performing ANY write.
     - *Phase 2 (All Writes)*: Executes `txn.update(appointmentRef, updates)`, decrements rate-limit quota `txn.set(rateLimitRef, ...)`, and logs the immutable audit trail `txn.set(auditRef, ...)`.
  3. **Targeted Deployment & Verification**: Re-authenticated the Firebase CLI via `firebase login --reauth` and deployed specifically via `firebase deploy --only functions:reviewAppointment`, preventing artifact registry collisions from unrelated functions. Verified live on physical/emulator device: Approve button now transitions the appointment to `approved`, updates quotas, appends the audit log, and refreshes the committee dashboard seamlessly.
- **Resilient Admin Cloud Functions Integration & Self-Healing Token Claims**:
  1. **Root Cause Analysis (Failed to assign task: Firebase/function/unauthenticated)**: When an admin clicked "Assign Fieldwork Task" or "Assign Reviewer", the call failed with `unauthenticated` or `permission-denied`. The root cause was that `admin_appointment_mutations.ts` employed a rigid, synchronous `requireAdmin(request)` guard that inspected only `request.auth.token.role`. When an admin's token is freshly issued or if custom claims propagation is delayed, `request.auth.token.role` evaluates to `undefined`, causing the function to reject legitimate administrators. Furthermore, `AdminAppointmentDetailController` was directly calling `appointmentRepository` or direct callables without forcing an ID token refresh and without standardizing error handling.
  2. **Hardened Async Admin Guard (`admin_appointment_mutations.ts`)**:
     - Converted `requireAdmin` to an async function.
     - Performs a deactivation check against `/users/{callerUid}` in Firestore (`callerDoc.data()?.active === false || callerDoc.data()?.isActive === false`), throwing `permission-denied` immediately if deactivated.
     - Fast-paths callers with `request.auth.token.role === "admin"`.
     - Provides self-healing fallback: if the token claim is absent, checks `/users/{callerUid}.role === "admin"` in Firestore. If true, invokes `await auth.setCustomUserClaims(callerUid, {role: "admin"})` to backfill the claim for subsequent requests, then grants access.
     - Awaited in `assignReviewer`, `setConfirmedDate`, and `assignFieldworkTask`.
  3. **Standardized Client Invocation (`AdminFunctionsService`)**:
     - `AdminAppointmentDetailController` now routes all admin mutations through `ref.read(adminFunctionsServiceProvider).callAdminFunction(...)`.

- **Cloud Storage Rules 2-Read Cap & Pre-Generated Appointment ID Synchronization**:
  1. **Root Cause Analysis (KML / Document Read StorageException -13021 / Permission Denied)**: When an applicant attempted to open or download a KML boundary map or permission document in `AppointmentDetailScreen`, Firebase Storage threw `StorageException: User does not have permission to access this object (Code: -13021, HttpResult: 403)`. Investigation identified two distinct flaws:
     - *Quota Crash (Exceeding 2 Firestore Reads)*: Firebase Storage rules strictly enforce a limit of at most two Firestore document reads per rule evaluation. `isAssignedCommittee(appointmentId)` unconditionally called `let appt = firestore.get(...)` (Read 1) before evaluating `isCommittee()`. For applicants, `isCommittee()` returned `false`, and evaluation proceeded to `isOwningApplicant(appointmentId)`, which invoked `firestore.exists(...)` (Read 2) and `firestore.get(...)` (Read 3). The 3rd read crashed the rules engine with a quota violation, returning an immediate 403.
     - *ID Desynchronization*: In `BookingWizardViewModel.submitBooking()`, files were uploaded using `tempId = DateTime.now().millisecondsSinceEpoch.toString()`, storing files in `appointments/<tempId>/kml/...`. The Cloud Function `submitAppointment` then generated a separate random Firestore ID (`appointmentRef = db.collection('appointments').doc()`, e.g. `xyz123`). The appointment document was saved at `/appointments/xyz123`, while the storage path referenced `<tempId>`. When `storage.rules` evaluated `firestore.exists(/databases/(default)/documents/appointments/$(appointmentId))`, `appointmentId` was `<tempId>` (which never existed in Firestore), failing the ownership check.
  2. **Client ID Pre-Generation Pattern**: Added `String newAppointmentId()` to `AppointmentWriter` and `FirebaseAppointmentRepository` (`_firestore.collection('appointments').doc().id`). In `BookingWizardViewModel`, the real Firestore document ID is generated *prior* to uploading files. KML and permission files are uploaded to `appointments/<appointmentId>/...`, perfectly matching the Firestore document path.
  3. **Backend Cloud Function Adoption**: `SubmitAppointmentData` interface and transaction logic in `submit_appointment.ts` accept optional `appointmentId?: string`. When provided, the transaction binds `appointmentRef = db.collection('appointments').doc(data.appointmentId.trim())`, ensuring Storage and Firestore paths are 100% synchronized from inception.
  4. **Direct Uploader Metadata (`uploadedBy`)**: `StorageUploadService.uploadKmlFile` and `uploadPermissionDocument` embed `uploadedBy: uid` in `customMetadata`. In `storage.rules`, `isUploader()` checks `resource.metadata.uploadedBy == request.auth.uid`, authorizing client reads with **0** Firestore reads.

- **Riverpod Pull-to-Refresh Non-Collapsing Lifecycle, Scrollable Child Architecture & Tab State Preservation**:
  1. **Root Cause Analysis (Infinite Refresh Loops & View Disconnection)**:
     In Applicant role, `HomeScreen`, `MyBookingsScreen`, and `AppointmentDetailScreen` suffered from repeating refresh animations and scroll collapse due to five intersecting issues:
     - *ViewModel `refresh()` Destruction*: Calling `state = const AsyncLoading()` and invoking `build()` stripped existing cached data, triggered rebuilds outside Riverpod's synchronous context, and collapsed the scroll view to a 40px centered spinner while `RefreshIndicator` was active.
     - *Scroll Metric Disconnection*: In `MyBookingsScreen`, `RefreshIndicator` wrapped `bookingsState.when(...)`, placing non-scrollable `Center` and `EmptyStateWidget` directly under `RefreshIndicator`. Mid-refresh state transitions destroyed scroll metrics and caused infinite refresh loops.
     - *Startup Auth Race*: Reading `ref.watch(authViewModelProvider).value` synchronously yielded `null` during startup loading, emitting empty dummy data before re-running a second time once auth resolved (causing visual flicker).
     - *Tab View Unmounting*: `AppointmentDetailTabScreen`'s `.when(loading: ...)` unmounted `AppointmentDetailScreen` during background list refreshes.
     - *`AppUser` Value Equality*: Lacking `operator ==` and `hashCode` caused every session reload/check to be treated as a state change.
  2. **Non-Collapsing Refresh Pattern**:
     In `HomeViewModel` and `MyBookingsViewModel`, `refresh()` directly executes `state = await AsyncValue.guard(...)` without calling `state = const AsyncLoading()`. Extracted data fetching to dedicated private helper methods (`_fetchDashboardData`, `_fetchBookings`). Existing data stays mounted during background re-fetch, eliminating layout shifts and flicker.
  3. **Guaranteed Scrollable Child Architecture**:
     `RefreshIndicator` requires an active scrollable child with `AlwaysScrollableScrollPhysics`. Empty and error states in `MyBookingsScreen` and `AppointmentDetailScreen` are wrapped inside `LayoutBuilder` + `SingleChildScrollView(physics: const AlwaysScrollableScrollPhysics())` with `ConstrainedBox(minHeight: constraints.maxHeight)`.
  4. **Auth State Synchronization**:
     ViewModels await `ref.watch(authViewModelProvider.future)` in `build()`, ensuring authentication and UID resolution complete before Firestore queries execute.
  5. **Tab State Preservation & Value Equality**:
     `AppointmentDetailTabScreen` uses `if (bookingsState.hasValue)` instead of blocking on `.when(loading: ...)`, preserving child detail views during background updates. `AppUser` implements structural `operator ==` and `hashCode` to prevent spurious widget rebuilds.
